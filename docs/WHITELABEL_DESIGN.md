# 화이트라벨 클론봇 설계 (방마다 봇 이름·프사 커스텀)

> 오너 아이디어(2026-10-26): "소담이 하나보다, **각 방마다 봇 프사·이름을 꾸미고 봇 이름을 지정**해서 파는 게 더 잘 팔릴 것 같다."
> 조사 = 전체 코드를 4갈래 서브에이전트로(실행구조·DB종속·결제오너·인프라) 실측. **이 문서는 설계만. 구현 아직 안 함.**
> 경쟁사 확인: GroupHelp·시큐리티봇도 이 방식(구매자가 BotFather로 자기 봇 만들어 토큰 넘기면 같은 코드·인프라가 그 봇을 돌림). **무료로 제공**(공유 인프라, 봇마다 토큰만).

---

## 0. 한 줄 결론

**가능하다. 그리고 생각보다 공사가 적다** — 딜러봇이 이미 "봇 토큰만 다르고 코드·서버는 같은" 멀티봇 선례이기 때문.
새로 만들 큰 공사는 딱 둘: **① 구매자 토큰 받아 클론 띄우는 첫 마법사 ② 미니앱 봇별 분리.** 나머지는 거의 설정(.env)·systemd 유닛 복제로 된다.

**제일 중요한 사실: 봇의 "보이는" 이름·프사·@아이디는 BotFather에서 구매자가 직접 정한다 = 우리 코드 0줄.**
구매자가 @BotFather에서 자기 봇을 만들면 이름·프로필 사진·소개글·@아이디가 전부 그 사람 것. 우리는 그 토큰으로 "같은 소담 두뇌"를 돌려줄 뿐. 오너가 원한 "방마다 봇 이름·프사"는 텔레그램이 공짜로 해준다.

## 1. 지금 구조 (기준선) — 이미 멀티프로세스다

한 서버(Hetzner VPS)에 봇이 **하나가 아니다**. 독립 systemd 유닛으로 여러 프로세스가 돈다:

| 프로세스 | 유닛 | 읽는 설정 | 역할 |
|---|---|---|---|
| 본체 | `sodam.service` → `python -m sodam` | `.env` | 폴링·핸들러·미니앱 내장 |
| 딜러 | `sodam-dealer.service` | `.env.dealer` (`SODAM_ENV`) | 게임 전용, **같은 DB** |
| 음성 | `sodam-voice.service` | `.env` | 도우미 계정 통화·노래 |
| 점검창구 | `sodam-diag.service` | `.env` | 127.0.0.1:8787 읽기전용 |
| SSH다리 | `sodam-sshws.service` | `.env` | 127.0.0.1:8023 |

**딜러 선례가 핵심.** `deploy/sodam-dealer.service` 주석: "다른 봇 토큰, 같은 DB_PATH". `config.py`도 "같은 DB_PATH 쓰면 두 봇이 포인트·설정·구독을 같이 본다".
→ **이미 "토큰 다름 + 코드 같음" 패턴이 존재.** 화이트라벨 클론 = 이 딜러 패턴을 일반화한 것.

`한 프로세스 = 한 봇 = 한 토큰` (`__main__.py` `ApplicationBuilder().token(cfg.telegram_token)`). 토큰은 기동 때 `.env`에서 한 번 읽음. 클론 N개 = 프로세스 N개.

## 2. 핵심 아키텍처 결정 — **봇별 별도 `.env` + 별도 DB 디렉터리** (옵션 A)

클론마다 `.env.clone1`, `.env.clone2` … + 각자 `DB_PATH=data/clone1/sodam.db` 식으로 디렉터리를 나눈다.

**왜 이게 거의 공짜냐:** 아래가 전부 `DB_PATH`의 부모 폴더 기준이라, **디렉터리만 나누면 자동 격리**된다.
- DB(`sodam.db`) · 봇별 API키(`keys.env`) · 음성 세션(`voice_assistant.session`) · 미디어 원본(`data/media`) · 음악 캐시(`data/music`) · 점검 토큰(`diag.token`) · 하트비트 파일

그리고 지금 코드가 오너·구독·예산을 전부 `chat_id`/`user_id` 평면으로만 저장하는데 — **별도 DB면 그 평면이 자동으로 "이 봇 것"이 된다:**
- `owners` 테이블 = 그 클론의 DB에 있는 사람 = **그 구매자**. (공유 DB면 A 구매자가 B의 오너 권한까지 먹음 — 위험)
- 매출·방목록·AI 예산 집계 = 그 DB 안에서만 = **봇 단위 자동 집계.**
- 기존 오너/TG관리자/봇관리자 3층 권한이 **각 클론 안에서 그대로** 돈다. 코드 수정 최소.

**공유 DB(딜러식)를 클론에 쓰면 안 되는 이유:** 딜러는 "같은 방을 같이 보는" 의도라 공유가 맞지만, 화이트라벨은 정반대(브랜드·오너·방이 서로 남남). 공유하면 `owners`·`counters`·`subscriptions`·예약공지 미디어·채널이 전부 섞인다. 섞인 걸 풀려면 모든 표에 `bot_id` 컬럼 + 필터를 넣는 대공사 + 오너/예산 누출 위험. → **별도 DB가 정답.**

### 2층 권한
- **본사오너(자이)** = 모든 클론 `.env`의 `OWNER_IDS`에 항상 포함 → 어느 클론에서나 오너. 전 클론 총괄.
- **구매자** = 자기 클론 DB의 로컬 오너. 자기 봇·자기 방만.
- TG관리자·봇관리자 층은 원래 방별이라 손댈 것 없음.

## 3. 첫 마법사 — 구매자 토큰 연결 (신규 공사 ①)

> 지금 코드엔 **런타임에 토큰 받아 봇 띄우는 경로가 전무.** 토큰은 오직 기동 때 `.env`에서만. 이게 최대 신규 공사.

### 흐름 (GroupHelp 방식)
1. 구매자가 @BotFather에서 자기 봇 생성 → 이름·프사·@아이디 직접 설정 → **토큰** 받음.
2. 구매자가 그 토큰을 **본사 "소담 본사" 봇 1:1**(또는 자이에게)에 붙여넣음.
3. 본사가 검증(`getMe`로 토큰 진짜인지·봇 이름 확인) + 발급:
   - `.env.clone<N>` 생성: `TELEGRAM_BOT_TOKEN`, `DB_PATH=data/clone<N>/sodam.db`, `MINIAPP_PORT=879N`, `MINIAPP_URL`, `OWNER_IDS=본사+구매자`, `PAY_ADDRESS`(선택)
   - systemd 유닛 활성(템플릿 `sodam@clone<N>.service`, 딜러 유닛 복제)
   - Caddy 경로/포트 추가
4. `systemctl enable --now` → 구매자 봇이 같은 코드·자기 DB로 돈다.

### 자동화 수위 (오너 결정 필요)
- **(A) 반자동**: 구매자가 토큰 DM → 자이/클로드가 ssh로 발급. 지금 "자이가 서버 운영" 현실과 맞음. **시작점으로 권장.**
- **(B) 완전자동**: 본사 봇이 토큰 받아 `.env` 쓰고 `systemctl enable --now sodam@<slug>` 자동 실행. GroupHelp 수준. 서버 자동화·권한(systemctl sudo) 작업 필요.

### 토큰 보관
- 봇별 `.env.clone<N>` 평문(지금 `.env`와 같은 신뢰 모델, `ProtectSystem=strict`+UMask 0077 보호).
- `apikeys.py`는 **일부러** 봇 토큰 저장을 막아둠("토큰·DB경로 바뀌면 위험") → DB에 토큰 저장(옵션 B)은 "한 프로세스 멀티봇" 대공사를 동반하므로 비권장. **봇별 .env가 현실적.**

## 4. 기존 방 처리 (재설계) — **그대로 둔다**

- 지금 모든 방은 @sodam_ai_bot 하나 + 메인 DB. 이게 **"클론 0 = 본사 소담"**이다.
- 화이트라벨 출시해도 **기존 방은 메인 봇/메인 DB에 그대로.** 마이그레이션 필요 없음.
- 신규 구매자만 새 클론(새 DB). chat_id도 DB도 서로 남남이라 충돌 0.
- (드문 경우) 기존 방 주인이 "내 전용 브랜드 봇으로 옮기고 싶다" → 그 chat_id의 행들을 새 클론 DB로 복사하는 1회성 스크립트. 흔치 않으니 수동/스크립트로 충분. (공유 DB였다면 `chat_owner_bot` 매핑표가 필요했겠지만, 별도 DB면 불필요.)

## 5. 과금·오너·AI 예산

- **과금 단위 = 방당 유지** (방 1개 = 월 30 USDT). 구독 테이블·청구서·연장·만료알림이 전부 `chat_id` 키라 이미 완성품. "봇당 구독"으로 바꾸지 말 것(재설계 대공사).
- 구매자는 보통 자기 업자방 여러 개 관리 → 방당이면 "방 3개=90 USDT"로 매출이 자연 비례 + 본사 AI 원가(방별 사용량)와 정렬.
- **받는 지갑**: 지금 전역 1주소(금액 끝자리로만 구분). 클론마다 `.env`에 `PAY_ADDRESS`를 두면 구매자별 분리 가능(본사가 대신 받을지/구매자 지갑 직접인지는 비즈 결정, 코드상 둘 다 됨).
- **AI 예산 = 봇별 필수.** 지금 안전장치는 전역 `DAILY_USD_BUDGET`(프로세스당)+방별 한도뿐. 별도 DB면 **클론 프로세스의 `DAILY_USD_BUDGET`이 곧 그 구매자 봇의 하루 상한** = 코드 0, env 값만. `구매자(봇) 예산 ⊃ 방 예산` 2단으로 자연 확장. 본사 OpenAI 키 공유, 구독료로 회수.
- **본사 매출 전체보기**: 지금 `_ROOMS_SQL`이 한 DB의 `chat_id<0` 전체를 훑음 = 오너가 전체 매출 봄. 별도 DB면 **클론 DB들을 가로질러 합산하는 얇은 본사 집계 도구** 하나 새로 필요(소소).

### 구독 안 한 클론 처리
- 기존 정책 그대로: **AI·게임·예약공지·리포트는 끄고(만료), 캡차·도배·금지어 등 모더레이션은 항상 무료.** (`subscription.py`가 이미 약속한 바)
- 클론은 봇 단위 소유 → **봇 구독 만료 시 그 봇 전 방 AI 일괄 중지** = `billing.active` 검사를 "방 구독 AND 봇 구독"으로 AND 한 줄 추가.
- 체험: 지금 방 단위지만, 클론은 "봇 전체 N일 체험"이 자연스러움(클론 .env `TRIAL_DAYS`).

## 6. 난관 — 미니앱 (신규 공사 ②)

**미니앱 initData 서명이 봇 토큰별이라 봇마다 분리돼야 한다.** (`miniapp.py` HMAC 검증이 `WebAppData`+봇토큰)
- 미니앱 서버 하나(포트 8790)를 여러 봇이 공유하면, 봇 B 요청(B 토큰 서명)을 A 토큰으로 검증 → 전부 403.
- **해결(쉬운 순)**: 봇별 `MINIAPP_PORT`(8790,8791…) + 봇별 `MINIAPP_URL` 명시 + Caddy를 봇별 경로(`/app1*`→8791)나 서브도메인(`clone1.<ip>.sslip.io`)으로. `miniapp.py`가 이미 env 포트를 읽으므로 코드 변경 최소, Caddyfile 작업이 주.

### 충돌 요약표

| 항목 | 봇별 필수? | 해결 |
|---|---|---|
| 봇 프로세스·토큰 | ✅ | 봇별 `.env` + systemd 유닛 |
| 미니앱 포트/URL/Caddy | ✅ | 봇별 `MINIAPP_PORT`+`MINIAPP_URL`+경로 |
| 하트비트 파일 | ✅ | 클론별 고유 파일명 |
| DB·세션·media·keys·토큰 | ✅(자동) | **별도 `DB_PATH` 디렉터리면 자동 분리** |
| 점검창구 8787·SSH 8023·Caddy 도메인·OpenAI 키 | 공유 OK | 그대로(단 diag `UNITS`에 클론 유닛 추가) |
| mediastore/file_id | 이미 대응 | `media_alias(bot_id,…)` 봇별 자동 |

## 7. 난관 — 음성 (오너 결정)

지금 음성 worker가 방에 보내는 모든 글은 **메인 .env 봇으로** 나감(`worker.py` `Bot(cfg.telegram_token)`). `voice_jobs`엔 bot_id 컬럼 없음.
- **(A) 클론별 worker**: 별도 DB면 무변경으로 자연스러움(자기 .env 토큰·자기 세션). 단 **도우미 사람 계정 N개 + api_id N개** 필요, 2 vCPU에선 금방 한계.
- **(B) 공유 worker**: `voice_jobs`에 bot_id 추가 + worker가 job의 bot_id로 해당 클론 봇 토큰 골라 전송(멀티 Bot 캐시) = **명확한 코드 작업.** 도우미 계정 1개로 여러 브랜드 방 입장은 텔레그램상 가능.
- 음성은 2차로 미뤄도 됨(클론 초기엔 음성 없이 출시 가능).

## 8. "소담" 하드코딩 571곳 — 2차 과제

- **보이는 브랜드(@아이디·이름·프사)는 BotFather = 코드 0.** 이것만으로 오너 요구의 핵심은 충족.
- 다만 AI가 자기를 "소담이야"라고 말하는 persona·호출어·안내서(`prompt.py`·`guide/*.md`)는 "소담" 하드코딩. 완전 화이트라벨(봇이 자기를 구매자 브랜드명으로 지칭)하려면 `cfg.bot_name`/`call_names` 파라미터화 확장 필요. → **2차.** 1차는 @username/프사만 구매자 것, 두뇌는 "소담"이어도 출시 가능.

## 9. 단계별 로드맵 (제안)

**1차 (최소 출시 — 딜러 패턴 복제)**
- systemd 템플릿 `sodam@<slug>.service` + 클론 `.env` 양식(토큰·DB_PATH·MINIAPP_PORT·OWNER_IDS·PAY_ADDRESS·TRIAL_DAYS)
- 반자동 토큰 연결(구매자 DM → 자이/클로드 ssh 발급)
- 봇별 별도 DB 디렉터리 → 오너·구독·예산 자동 격리
- 미니앱 봇별 포트/URL/Caddy 경로
- diag `UNITS`에 클론 유닛 추가, 하트비트 파일명 봇별

**2차**
- 본사 봇 자동 발급(토큰 DM → systemctl 자동)
- 본사 전체 매출 가로 집계 도구
- `billing.active` = 방 AND 봇 구독
- 음성 멀티봇(공유 worker + bot_id, 또는 클론별)

**3차 (완전 화이트라벨)**
- persona·호출어·안내서 브랜드 파라미터화("소담" 하드코딩 제거)
- 구매자용 셀프 브랜딩 화면(봇 설명·웰컴 등)
